## Блокеры


### 2. JSON-RPC-биндинг диспатчит весь реестр, включая REST-методы

Источник: А+Б. Воспроизведено.

`jsonrpc` передаёт любой метод в `core.call` ([jsonrpc.ts:134](src/jsonrpc/jsonrpc.ts#L134)). REST-объявленный `Admin.wipe` вызывается через `/rpc` с params `{ body: { confirm: true } }`, хотя в OpenRPC его нет ([jsonrpc/docs.ts:44](src/jsonrpc/docs.ts#L44)). Middleware самого метода при этом работает; не работает то, что стоит снаружи: guard на REST-роуте или прокси.

[MIGRATION.md:548](MIGRATION.md#L548) утверждает обратное: «`jsonrpc(composer)` picks up the `fn` endpoints».

Что сделать: биндинг по умолчанию обслуживает только свои эндпоинты (`jsonrpc` — без `rest`-меты); доступ к чужим — явной опцией. До исправления — раздельные реестры или авторизация в `use` контракта.

### 3. REST-клиент молча теряет тело запроса

Источник: А. Воспроизведено.

Клиент собирает тело только из `properties` корня body-схемы ([client/index.ts:98-106](src/client/index.ts#L98-L106), [:132-139](src/client/index.ts#L132-L139)).

- `body: z.record(z.string(), z.number())`: `client.Shapes.meta({ a: 1, b: 2 })` отправляет `POST` без тела; обработчик получает `{}` и отвечает 200. Данные теряются без ошибки.
- `body: z.discriminatedUnion(…)` (то же для union и intersection): тело не отправляется, сервер отвечает 422. Типы клиента требуют плоской формы `create({ kind: 'circle', r: 1 })`, а рантайм ждёт `{ body: … }`, и эту форму типы отвергают.

Что сделать: тело объектной схемы собирать зеркально серверу — все поля входа, не занятые `path` и `query`; обёртку `body` оставить только для массивов и скаляров.

### 4. REST: query перезаписывает проверенное поле body

Источник: Б. Воспроизведено.

Результаты схем сливаются в порядке `body → query → path` ([rest.ts:82-118](src/rest/rest.ts#L82-L118)). Если query-схема пропускает лишние ключи, одноимённое поле из query заменяет значение, проверенное body-схемой.

```ts
post('/charge', {
  body: z.object({ amount: z.number().positive() }),
  query: z.looseObject({ ref: z.string().optional() }),
});
// POST /charge?amount=-5  {"amount":10}  →  обработчик получает amount: "-5"
```

Срабатывает с `z.looseObject` и с arktype по умолчанию (`type({ 'ref?': 'string' })` сохраняет необъявленные ключи). Обычный `z.object` лишние ключи срезает и не подвержен.

Что сделать: отклонять коллизии имён между срезами либо брать из каждого среза только ключи, объявленные его схемой.

### 5. REST: чужие ошибки с полем `status` утекают клиенту

Источник: А. Воспроизведено.

Проверка в [rest.ts:241-246](src/rest/rest.ts#L241-L246) — duck typing по числовому `status`. Ошибка стороннего SDK вида `Object.assign(new Error('Incorrect API key provided: sk-live-…'), { status: 401 })` уходит клиенту как `401 {"detail":"Incorrect API key provided: sk-live-…"}`.

Там же теряется `data`: `throw new RpcError(-32000, 'Conflict', { code: 'DUP', retryAfter: 5 }, 409)` даёт `409 {"detail":"Conflict"}`. Схему тела, объявленную в `resp` для 409, отдать невозможно.

Что сделать: принимать статус только от `RpcError` или отдельного `HttpError`; тело ошибки брать из `data`.

### 6. `compose()` исполняет inject-фабрики и конструкторы с фейковым ctx

Источник: А. Воспроизведено на собранном `dist`. В PROGRESS записано как долг «warnMissingHandlers probe».

Проба `warnMissingHandlers` ([core/index.ts:139-159](src/core/index.ts#L139-L159)) при старте вызывает фабрики и конструкторы сервисов на Proxy-заглушке. Синхронные исключения ловятся, отклонённый промис async-фабрики — нет:

```js
compose({ Svc }, { inject: { user: async (ctx) => {
  const [, payload] = ctx.request.headers.get('authorization').split('.');
  return JSON.parse(atob(payload)); // падает на заглушке
} } });
// compose() возвращается, затем процесс завершается с кодом 1 (unhandled rejection)
```

Что сделать: убрать пробу. Проверка на этапе вызова уже есть ([core/index.ts:241-243](src/core/index.ts#L241-L243)).

### 7. REST: query-массивы не переживают round trip собственного клиента

Источник: А+Б. Воспроизведено.

Для `query: z.object({ tag: z.array(z.string()) })`:

| Вызов клиента | Запрос | Ответ |
|---|---|---|
| `list({ tag: ['a', 'b'] })` | `?tag=a&tag=b` | 200 |
| `list({ tag: ['a'] })` | `?tag=a` | 422 (`expected array, received string`) |
| `list({ tag: [] })` | без ключа | 422 (`received undefined`) |

Сервер превращает одиночное значение в строку ([rest.ts:223-227](src/rest/rest.ts#L223-L227)).

Что сделать: при создании `rest()` определить array-поля по JSON Schema query-части и всегда отдавать их массивом, включая пустой.

### 8. Пакет перестал загружаться через `require`

Источник: Б. Воспроизведено на Node 22.21.1.

`require('@chord-ts/rpc')` возвращает `ERR_PACKAGE_PATH_NOT_EXPORTED`: в [package.json:23-35](package.json#L23-L35) объявлено только условие `import`. На `origin/main` пакет был CommonJS (`"type": "commonjs"`, сборка `tsc` с `module: commonjs`), поэтому для CJS-потребителей v1 это поломка. [README.md:125](README.md#L125) при этом обещает, что существующие импорты продолжают работать.

Что сделать: принять решение. Варианты — условие `default` вместо `import` (по документации Node тогда `require` ESM-пакета работает на Node ≥ 20.19 и ≥ 22.12; не прогонялось), двойная сборка либо явное предупреждение в MIGRATION.

## Средние

### 9. DI молча отключается при наследовании и при ES5-таргете

Источник: А. Воспроизведено.

`paramNames` ищет `constructor(` в исходнике класса ([core/index.ts:69-76](src/core/index.ts#L69-L76)). Для `class Child extends Base {}` с неявным конструктором он возвращает `[]`: зависимости не передаются, `this.db` равно `undefined`, compose-гард ([core/index.ts:202-214](src/core/index.ts#L202-L214)) молчит. То же при сборке, компилирующей классы в функции (SWC с таргетом ES5).

Что сделать: на compose сравнивать `Ctor.length` с числом найденных ключей и падать при расхождении; для подклассов без конструктора брать ключи базового класса.

### 10. Middleware вокруг стрима завершается до первого события и не видит вызов

Источник: А. Воспроизведено.

Цепочка оборачивает только создание итератора ([core/index.ts:330-345](src/core/index.ts#L330-L345)). Порядок: `mw: before → mw: finally → первое событие`. Guard работает, но транзакции, ALS-контекст и трейсинг-спаны закрываются до итерации.

Middleware получает только `ctx`, без имени метода и params. Логирование, метрики и кэш написать нельзя, хотя [MIGRATION.md:393](MIGRATION.md#L393) советует писать кэш как middleware.

### 11. Стандартные JSON-RPC клиенты не могут вызвать метод без аргументов

Источник: А. Воспроизведено.

- `in: z.void()` отвергает `params: []` и `params: {}` с `-32602`; проходит только отсутствие `params`.
- `in: z.object({ tz: z.string().optional() })` отвергает отсутствие `params` и `[]`.
- OpenRPC для void-метода объявляет `params: []`, и типовой инструмент отправит именно пустой массив.

Что сделать: для void-схемы считать `[]`, `{}` и отсутствие `params` эквивалентными; для объектной схемы подставлять `{}` при отсутствии `params`.

### 12. Типы расходятся с проводным контрактом

Воспроизведено (tsc и рантайм).

- **Аргумент клиента типизируется после `transform`** (Б). Тип берётся из сигнатуры обработчика ([client/types.ts:54-56](src/client/types.ts#L54-L56)), а она — из выхода входной схемы ([core/types.ts:54-56](src/core/types.ts#L54-L56)). Для `z.string().transform(s => s.length)` клиент принимает `3` и отвергает `'abc'`; сервер наоборот. Поле с `.default()` клиент требует обязательно. `AnySchema` несёт только выходной тип, входной взять неоткуда.
- **Кортеж с rest-элементом** (А). Для `z.tuple([z.string()], z.number())` тип обработчика — один аргумент-массив, рантайм вызывает `handler('a', 1, 2)` ([core/index.ts:193](src/core/index.ts#L193)).
- **Метод без схемы** (А). Решение принимается по `handler.length` ([core/index.ts:300-304](src/core/index.ts#L300-L304)): `sum(a, b = 0)` с `[1, 2]` получает `a = [1, 2]`; `rest(...xs)` получает `xs = [[1, 2]]`.

### 13. Клиент не проверяет конверт ответа

Источник: А+Б. Воспроизведено.

- HTTP ([client/index.ts:52-62](src/client/index.ts#L52-L62)): ответ 200 с телом `{"foo":1}` или пустым телом резолвится в `undefined`; версия протокола, наличие `result` и совпадение `id` не проверяются.
- WebSocket ([client/index.ts:220-277](src/client/index.ts#L220-L277)): вызов после `close` и ответ с `id: null` не завершаются никогда, потому что `timeout` по умолчанию выключен.

### 14. `out` по умолчанию не применяется в рантайме

Источник: А. Воспроизведено.

Обработчик с `out: z.object({ id })`, вернувший ещё и `passwordHash`, отдаёт его на провод; с `validateOut: true` поле срезается ([core/index.ts:286](src/core/index.ts#L286)). События стримов валидируются всегда. Стоит включить по умолчанию.

### 18. ReDoS в REST-роутере при нескольких плейсхолдерах в сегменте

Источник: Б. Воспроизведено.

`compilePath` запрещает соседние плейсхолдеры, но допускает несколько жадных групп через литерал ([rest.ts:143-164](src/rest/rest.ts#L143-L164)). Время на один несовпадающий путь:

| Шаблон | Длина пути | Время |
|---|---|---|
| `/f/{name}.{ext}` | 16 КБ | 185 мс |
| `/f/{a}-{b}-{c}` | 2 КБ | 1,0 с |
| `/f/{a}-{b}-{c}` | 4 КБ | 7,9 с |
| `/f/{a}-{b}-{c}-{d}` | 0,8 КБ | 6,8 с |

Применимость зависит от того, какие шаблоны объявит разработчик.

Что сделать: один плейсхолдер на сегмент либо сопоставление по сегментам без регулярного выражения.

### 19. Клиент пишет чувствительные данные в лог

Источник: А+Б. v2 — воспроизведено (вывод наблюдался в тестах), v1 — по чтению.

На каждый не-2xx, включая штатные 422 и 404 REST, v2-клиент пишет в `console.error` полный URL с query, заголовки ответа (кроме `set-cookie` и `authorization`) и 200 символов тела ([client/index.ts:189-197](src/client/index.ts#L189-L197)). v1-клиент дополнительно пишет параметры вызова ([v1/client/defaults.ts:101-112](src/v1/client/defaults.ts#L101-L112)). Для SSR это попадает в серверные логи.

Что сделать: по умолчанию логировать только статус; подробности — через явный opt-in или пользовательский логгер.

### 20. v1 `cacheMiddleware` обходит валидацию и может обойти авторизацию

Источник: Б. По чтению. В PROGRESS записано как долг H5; это не регрессия v2, но код экспортируется из `./middlewares`.

[v1/middlewares/cache.ts:35-66](src/v1/middlewares/cache.ts#L35-L66):

- при попадании в кэш ответ возвращается до `next()`, последующие middleware и валидация не выполняются;

- при промахе middleware сам вызывает обработчик, не проверяя, упал ли следующий middleware, и минуя штатную валидацию ([v1/server/index.ts:389-448](src/v1/server/index.ts#L389-L448)).
