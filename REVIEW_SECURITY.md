# Ревью безопасности: проверка и приоритеты

Ветка `v2`, коммит `0e0de22` (`@chord-ts/rpc@2.0.0-beta.1`).

Документ проверяет находки внешнего ревью: каждая сверена с кодом, ключевые подтверждены запуском PoC-теста. Ниже — насколько всё это серьёзно, как это можно использовать и в каком порядке исправлять.

## Итог

- **Все проверенные находки подтвердились.** Ложных срабатываний нет.
- Две оказались серьёзнее, чем в исходном ревью: **MCP-контекст** (кроме обхода авторизации, один запрос роняет процесс) и **утечка в `invalid-output`** (наружу уходит весь объект, включая поля вне схемы).
- **Критичных дыр «в любой конфигурации» нет.** Каждая требует определённого способа использования библиотеки. Но часть этих способов типична, а последствия — обход авторизации, утечка чужих данных, отказ в обслуживании.

## Находки подробно

### 1. v2 MCP: асинхронная фабрика контекста

**Где:** [src/mcp/vercel/index.ts:105-111](src/mcp/vercel/index.ts#L105-L111), тип опции — [строка 78](src/mcp/vercel/index.ts#L78).

```ts
const chordCtx = opts.ctx && req ? opts.ctx(req) : {};
```

- Результат фабрики не ожидается: в `core.call` уходит `Promise`.
- Тип `ctx?: (req: Request) => unknown` разрешает async-фабрику без предупреждения.
- Без `req` (например, не-HTTP транспорт) настроенная фабрика пропускается, вызов идёт с `{}`.

**PoC:** фабрика бросает `unauthorized` → обработчик тула выполняется, `this.ctx` равен `[object Promise]`; отклонённый промис становится unhandled rejection.

**Как использовать:** типичная фабрика — `async (req) => { const s = await getSession(req); if (!s) throw … }`. Атакующий отправляет MCP-запрос с невалидным токеном:

- обработчик выполняется, хотя проверка доступа не пройдена;
- отклонённый промис никто не ловит, и Node ≥15 по умолчанию завершает процесс. Достаточно одного запроса без учётных данных, чтобы положить сервер. На serverless падает инстанс, но запросы можно повторять.

Если проверка вынесена в middleware, а не в фабрику, обхода не будет (`ctx.user` окажется `undefined`), но MCP перестаёт работать у всех, а падение от отклонённой фабрики остаётся.

**Исправление:** `await opts.ctx(req)` до `core.call`. Если фабрика настроена, но `req` нет или фабрика бросила — не вызывать метод и вернуть ошибку. Сузить тип до `(req: Request) => unknown | Promise<unknown>` и явно задокументировать.

### 2. v2: автоматическая публикация методов прототипа

**Где:** [src/core/index.ts:131-139](src/core/index.ts#L131-L139). Тест приватности [src/core/register.test.ts:82-85](src/core/register.test.ts#L82-L85) проверяет только нативный `#private`.

Любой callable-метод прототипа без `$`-контракта становится эндпоинтом без схемы и без `contract.use`. Модификаторы TS `private`/`protected` после компиляции исчезают. Глобальный middleware (`compose({ use })`) при этом применяется.

**PoC:** `private async wipeAll()` вызвался по JSON-RPC как `Acc.wipeAll` и вернул результат.

**Как использовать:**

```ts
class Users {
  static $update = fn({ ... });
  update = Users.$update(async (p) => { checkOwner(p); return this.applyPatch(p); });
  private async applyPatch(p) { /* пишет в БД без проверок */ }
  private async grantRole(userId, role) { ... }
}
```

Любой пользователь, прошедший глобальный middleware, вызывает `Users.grantRole` с произвольными параметрами — без валидации и без проверок метода. Имена легко угадать, в open-source проектах они видны в коде. Внутренние методы обычно рассчитаны на то, что вызывающий уже всё проверил, поэтому это прямое повышение привилегий.

**Исправление:** по умолчанию публиковать только методы с явным контрактом. Автоматическую регистрацию оставить отдельной опцией совместимости (opt-in). Добавить тест на TS `private`.

### 3. v1: `cacheMiddleware`

**Где:** [src/v1/middlewares/cache.ts:35-67](src/v1/middlewares/cache.ts#L35-L67).

- Ключ — только метод и параметры (`callToKey`).
- При попадании ответ возвращается до последующих middleware.
- При промахе middleware сам вызывает `descriptor.value.apply(target, …)`: в обход валидации и DI, причём `target` — прототип, а не инстанс.
- После этого диспетчер вызывает обработчик ещё раз (см. находку 4).

**PoC:** на обычном пути обработчик вызван **2 раза**. С запрещающим middleware после кэша клиент получает `forbidden`, но обработчик **уже выполнился**.

**Как использовать:**

- Пользователь A вызывает `Profile.me()`, ответ кэшируется. Пользователь B вызывает `Profile.me()` и получает профиль A. Никаких действий от атакующего не нужно — данные утекают при обычной работе.
- Если кэш стоит до авторизации, неавторизованный клиент читает всё, что уже есть в кэше.
- Если кэш стоит до запрещающей проверки, метод выполняется, хотя клиент видит отказ.
- Двойной вызов на обычном пути — двойные списания и письма у неидемпотентных методов.

**Исправление:** убрать прямой вызов `descriptor.value`. Кэшировать результат единственного штатного вызова после авторизации и валидации. Пользователя и tenant включать в ключ либо исключать персональные методы из кэша.

### 4. v1: остановка цепочки middleware

**Где:** [src/v1/server/index.ts:323-350](src/v1/server/index.ts#L323-L350), [строки 389-406](src/v1/server/index.ts#L389-L406).

Если middleware не вызвал `next()` и ничего не вернул, `runMiddlewares` возвращает `res: undefined`. Диспетчер проверяет `if (res)`, а не факт прохождения цепочки, и вызывает обработчик. Последующие middleware (в том числе другие проверки доступа) при этом пропускаются.

**PoC:** middleware без `next()` и без возврата → обработчик выполнился, ответ `"ok 5"`.

**Как использовать:** документация ([src/v1/server/index.ts:141](src/v1/server/index.ts#L141)) показывает отказ через возврат ответа, и этот путь работает. Но привычный по Express/Koa паттерн `if (!user) return;` молча пропускает запрос к обработчику: атакующий вызывает любой метод без авторизации. Насколько это массово, зависит от того, как пользователи пишут middleware.

**Исправление:** сделать вызов обработчика последним шагом самой цепочки (как `runChain` в v2). Без `next()` выполнение не доходит до обработчика независимо от возвращённого значения.

### 5. v1: валидация параметров

**Где:** [src/v1/server/index.ts:425-448](src/v1/server/index.ts#L425-L448), декоратор — [строки 563-578](src/v1/server/index.ts#L563-L578), адаптер — [src/v1/validators/zod.ts](src/v1/validators/zod.ts).

- `@rpc({ in })` нормализует `config.in`, но не сохраняет его: строка с `validators` закомментирована.
- Адаптер при отсутствии валидатора возвращает `success: true`, поэтому проверка молча пропускается.
- Даже с `@val` цикл идёт по переданным параметрам, а не по объявленным валидаторам: пропущенная обязательная позиция не проверяется.

**Как использовать:** разработчик объявил `@rpc({ in: [z.string()] })` и считает вход проверенным. Атакующий передаёт объект `{"$ne": null}` вместо строки — классическая NoSQL-инъекция в запрос к Mongo (например, вход без пароля). Другие варианты — неожиданные типы и большие объекты, на которых обработчик падает.

**Исправление:** сохранять `in` из `@rpc` и проверять каждую объявленную позицию, включая отсутствующие значения, до вызова обработчика.

### 6. v2 JSON-RPC: утечка через `invalid-output`

**Где:** [src/core/index.ts:307-313](src/core/index.ts#L307-L313), [src/jsonrpc/jsonrpc.ts:71-80](src/jsonrpc/jsonrpc.ts#L71-L80).

При `validateOut: true` исходные issues валидатора уходят клиенту в `error.data`. REST этим не страдает: для `invalid-output` он отдаёт общий 500 ([src/rest/rest.ts:369](src/rest/rest.ts#L369)). MCP-мост отдаёт только `message`.

**PoC (Valibot):** обработчик вернул `{ name: 1, passwordHash: 'SECRET' }` при схеме `{ name: string }`. Клиент получил в `path[].input` **весь объект**, включая `passwordHash`, которого в схеме нет.

**Как использовать:** напрямую атакующий это не вызывает. Нужно найти запись, которая не проходит схему ответа (старые данные, `null` в поле, неожиданный тип). Тогда в ошибке приходит весь объект, включая скрытые поля.

**Исправление:** для `invalid-output` возвращать общее сообщение без `data` (как REST), исходные issues — только в серверный лог.

### 7. v1: внутренние ошибки уходят клиенту

**Где:** [src/v1/server/index.ts:455-466](src/v1/server/index.ts#L455-L466).

Клиент получает `message: e.message` и `data: [e]`. Ошибки middleware тоже отдаются с исходным сообщением.

**Как использовать:** разведка. Сообщения драйверов БД и runtime-ошибок раскрывают строки подключения, пути, фрагменты SQL, имена внутренних полей.

**Исправление:** для неожиданных ошибок — общее сообщение и идентификатор события; детали — через `onError` в лог.

### 8. v2 JSON-RPC: batch без лимитов

**Где:** [src/jsonrpc/jsonrpc.ts:153-162](src/jsonrpc/jsonrpc.ts#L153-L162).

Все элементы batch запускаются через `Promise.all` без ограничений.

**Как использовать:** один HTTP-запрос с тысячами элементов, каждый вызывает тяжёлый метод. Rate limit по числу HTTP-запросов этого не видит. Лимит размера тела (в Express по умолчанию 100 KB) сдерживает лишь частично: в 100 KB помещаются тысячи коротких вызовов.

**Исправление:** два независимых лимита — размер batch до диспетчеризации (ответ `-32600` при превышении) и число одновременно выполняемых методов.

### 9. v1: коллизия одноимённых классов

**Где:** [src/v1/server/index.ts:92-99](src/v1/server/index.ts#L92-L99), [строки 368-387](src/v1/server/index.ts#L368-L387).

Реестр `Composer.methods` статический, ключ — `constructor.name` + имя метода.

**PoC:** `Composer`, собранный с классом `Svc` из модуля A, вернул реализацию `Svc` из модуля B.

**Как использовать:** если в процессе два `Composer` (например, публичный и админский API) с одноимёнными классами, публичный эндпоинт может выполнить реализацию и middleware другого класса. В минифицированных бандлах вероятность выше: terser по умолчанию переименовывает классы в короткие имена.

**Исправление:** хранить метаданные по идентичности конструктора (`WeakMap`), таблицу маршрутов строить отдельно для каждого `Composer`.

## Критерий приёмки

При отказе в авторизации, отсутствии обязательного контекста или ошибке валидации **число вызовов обработчика должно быть равно нулю**, в том числе при попадании в кэш. Тест должен считать вызовы обработчика: проверки, что вернулся ответ с ошибкой, недостаточно.

Регрессионные тесты, которые нужно добавить:

- MCP: async-фабрика бросает → 0 вызовов, нет unhandled rejection; фабрика настроена, `req` нет → 0 вызовов.
- v2: метод с TS `private` без контракта → `MethodNotFound` (при выключенной опции совместимости).
- v1: middleware без `next()` и без возврата → 0 вызовов.
- v1 cache: обычный путь → ровно 1 вызов; запрещающий middleware после кэша → 0 вызовов; разные пользователи → разные записи кэша.
- v1: `@rpc({ in })` с неверным типом и с пропущенным параметром → `InvalidParams`, 0 вызовов.
- JSON-RPC: `invalid-output` → ответ без `data`.
- JSON-RPC: batch больше лимита → отказ до диспетчеризации.
